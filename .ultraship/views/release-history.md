### 0.28.0 known limitations

- **A hook blocks the run loop while it runs.** `Observer::event` is synchronous and returns a `Flow` the loop acts on immediately, so the step that emitted the event waits for every matching hook. That is the property that makes `on_failure = "cancel"` mean anything — a hook that answered after the run had moved on could refuse nothing — and it means pointing a `run` hook at `token`, which is emitted per streamed token, is a decision to spawn a process that often. The guide says so beside the feature rather than in a footnote.

- **Hooks do not accumulate across scopes.** Unlike `[[policy.layers]]` and `[[agent]]`, the array is deliberately not in `APPENDING`, so a later scope replaces it whole: one `[[hook]]` in `io.local.toml` silently discards every hook the user-scope file declared. A half-appended set of hooks would be a set nobody wrote, and `Config::sources()` says which file won.

- **An `append` hook is serialized within this process and nowhere else.** It opens its file per event rather than holding a handle, and a lock keeps a sub-agent tree from interleaving halves of two events. A second *process* appending to the same log is not coordinated by anything, and there is no rotation and no size cap.

- **A hook's output is discarded.** `stdout` and `stderr` go to `null`, because a library must not write to its caller's terminal, so a hook talks by exiting non-zero. A failure is traced at warn level with the hook's index and the event tag, and never with the event itself — a `started` carries the goal.

- **A hook grants nothing.** It is not a permission mechanism: it cannot approve an action, deny one, alter an argument or answer an `approval_requested`. The only thing it can do to a run is end it, and only when the operator wrote `on_failure = "cancel"`. The boundary is still the `Policy` the caller loaded.

- **Refusing `[[hook]]` in the project scope does not make a cloned repository safe.** `[[mcp]]` still names a command, `[toolchain]` still names an argv, and a `[[policy.layers]]` entry can still allow what the defaults did not. One specific hazard is narrowed, and the contract, the guide and the changelog each say which array and no more.

- **One restore point per file per run.** `rewind` is all-or-nothing back to the run's start: there is no per-edit undo, no rewind to a chosen step, and no redo. That is what bounds the storage to the number of files a run touched rather than the number of edits it made, and it is the only definition under which "undo what this run did" is one operation rather than five.

- **A previous file over 1 MiB or one that is not valid UTF-8 cannot be put back.** It is recorded `Unkept`, `rewind` answers `NotKept` with the reason, and the file is left exactly as the run left it — reported rather than guessed at, and never truncated. An existing path that could not be read for any other reason is `Unkept` too rather than `Absent`, because folding a permission error into "the file did not exist" would make a rewind *delete* something whose contents were never read.

- **Only `write_file` and `edit_file` take a snapshot.** A file changed by `shell`, by `exec`, or by a git built-in has no restore point and answers `NotRecorded`. So does one whose bookkeeping row could not be written, which is warned about and swallowed exactly as an edit row is — so `NotRecorded` means "no restore point", not "the run did not write it".

- **`rewind` takes one path per call and is not transactional.** Undoing a whole run is a loop the caller writes, and it can be interrupted halfway.

- **`${cmd:}` still has no timeout.** 0.27.0's standing limitation, carried deliberately rather than fixed by proximity because this release wrote a bounded wait ten lines away. `Config::discover` is the caller's own call before any run exists; a hook fires inside a run loop. They are not the same hazard and one bound does not follow from the other.

- The record is sealed before the crates.io upload, which follows the two merges and the GitHub Release. `mode: published` states the authorized target.

- Stall detection is a heuristic over two signals, not a proof. It reads whether a write changed the file's bytes and whether a tool call repeated. - TaskContract has public fields and is not #[non_exhaustive], so the new tools and skills fields do break struct-literal construction. The public API is additive in every other respect (42 items added, 0 removed, 0 signature-changed) and the type documents the builder as the supported path, which is the pattern 0.8.0 set when it added mcp the same way.


### 0.8.1 known limitations

- A passing execution gate is evidence that the stated criterion was satisfied. It is not proof the artifact is correct, and this release does not make it one — a gate asserting `hello() == 42` stays silent about everything else the file does. Hardening the gate against the subject makes the evidence trustworthy; it does not widen what the evidence covers.

- A subject that legitimately defines a macro named after a prelude macro the criterion invokes (`assert`, `assert_eq`, and the rest of the re-imported list) now fails to compile with E0659 rather than passing. This is the shadowing defence working as designed and it cannot distinguish a hostile redefinition from an innocent one. A macro under any other name is unaffected.

- Verification costs more compiler spawns: the compile-only gates went from one to two and the test gates from two to four. On the reference machine that is roughly 29 ms to 59 ms and 290 ms to 381 ms. A caller running a large fan-out of gated agents pays this per gate, and `EachCompilesRust` pays its share per listed file. The reverted two-crate structure was cheaper; it was also wrong.

- The record is sealed before the crates.io upload. `mode: published` states the authorized target and the publish step is the last in the sequence — feat→develop merge, develop→main merge, GitHub Release, then `cargo publish`. If the upload fails, the correction is a forward patch, not an edit to this record.

- F5's serde half is vacuous: `Verification` has no serde derive, so there is no representation to round-trip. The criterion was written expecting one. The substantive guarantee — a 0.8.0 caller's `Verification` values compile unchanged — holds and is verified.

- The `#![cfg(any())]` vector was found by reproducing the recorded bypass, and the compile-only hole by reviewing gates the contract predicted were safe. Both were cheaper to find than the bypass that started this release. No systematic search for further vectors against the gate was performed, so the honest claim is that three known classes are closed, not that the gate is exhaustively hardened.

- The offline suite passed 186 tests against a build that failed the live run, because every test wrote `pub fn hello` and inherited the structure's own assumption. The regression is now pinned, but the general lesson is not: a structural defence must be checked against honest code that does NOT resemble the tests already written for it.


### 0.8.0 known limitations

- This record was sealed on feat/0.8.0 before the crates.io upload, because the repo's release order puts publication last — after the feat→develop and develop→main merges and the GitHub Release. `mode: published` is the contract's authorized target and the sequence the owner directed, not a claim that the upload had already happened when the file was written.
- F9 is met in substance but not as literally worded. The contract says a server whose binary does not start is "handled by the 0.2.0 retry/recovery path"; it instead fails the run with a typed Error::Mcp at session construction, because connecting happens before step 1, retrying a missing binary cannot make it appear, and proceeding without a configured capability is the worse failure. The other three legs — tool error, per-call timeout, and a server killed mid-run — do go through the loop as recoverable observations, each with its own test.
- NF2 is proven indirectly. The whole pre-existing suite, including the 0.5.0 fan-out tests, runs green with the network act live, and the MCP session is shared by reference through Tree rather than per agent — but there is no dedicated timing benchmark asserting that egress checking does not serialize a 100-agent fan-out. Same shape of limitation 0.7.0 recorded for checkpointing.
- The harness governs the connections it opens, not the connections a running stdio MCP server opens for itself. That server is a separate process: the harness decides whether it may start (an exec check on the binary) and which of its tools may be called (an exec check on the namespaced name), and nothing more. Isolating a server's own egress needs OS-level containment, which is not built here.
- Calling an MCP tool needs a SECOND exec allowance, on the namespaced tool name, beyond the one that lets the server binary start. This is deliberate — it is what lets a policy admit a server and still refuse one of its tools — but it is easy to miss: the first live run connected the server, discovered its tools, offered them to the model, and refused every call. Documented in README and in examples/mcp_run.rs, but the failure mode is quiet.
- MCP resources, prompts, sampling, roots, and elicitation are not supported — tools only. Neither is OAuth: static credentials pass through configuration (headers, environment), but there is no interactive authorization flow. Both are excluded scope, not defects.
- Egress policy decides WHETHER a host may be reached, not how much may flow to it. There are no byte, rate, or bandwidth ceilings, no payload inspection, no TLS pinning, and no proxy or DNS-level enforcement — the check is in-process at the point the connection is opened.
- Redirects are now disabled on every built-in provider's HTTP client, to close the checked-then-redirected hole. A provider endpoint that legitimately relies on a 3xx would now surface it as a non-success status rather than following it.
- The live run used a single-agent workspace run. A live run of a 0.5.0 agent tree with MCP tools is not part of this release's evidence; the tree path is covered offline by the fan-out suite running green with the session wired in.
- In the live run the model satisfied the criterion by writing "echo:" rather than the full server reply. The criterion passed as written, and that the tool's output does reach the next prompt is pinned separately by an offline sentinel test — but the live artefact is thinner than the goal text asked for.
- MSRV rose from 1.75 to 1.87 and reqwest from 0.12 to 0.13, both forced by rmcp 2.2.0. Callers on an older toolchain cannot take 0.8.0.

### 0.7.0 known limitations

- NF5 concurrency has no dedicated 100+-agent timing test asserting non-serialization. Each agent commits its own step independently (per-agent unchecked_transaction, no new global lock over the 0.5.0 single-connection model), and the existing subagents fan-out suite now runs green with checkpointing default on — but "checkpointing does not serialize the fan-out" is proven indirectly, not by a dedicated concurrency benchmark.
- resume_tree_with_decision re-checks the approved write against the tree (root) policy, not the resumed child's narrowed policy (not reconstructed at the decision point; marked with a ponytail comment). A policy deny still blocks, and a remembered-allow cannot defeat a deny beneath it, but a child-specific deny of an action the tree policy allows is not re-enforced on that one performed write.
- The live example run happened to solve in a single step, so it demonstrates durable-store + idempotent-resume across a real process boundary rather than a live mid-run crash-and-continue. The mid-run continue path is proven deterministically and offline by the real-SIGKILL resume test; a live provider run that is genuinely interrupted mid-task is not part of this release's evidence.
- The literal 24h+ wall-clock unattended run is out of scope by design (contract excluded scope). The horizon is proven by the real-SIGKILL resume test plus a 250-step long unattended run that checkpoints throughout; a real multi-hour run is not executed here.
- Resume is single-machine only — checkpoints are the local rusqlite store and resume runs on the same host (product.yaml: local, single-user). No distributed or cross-machine checkpoint/handoff.
- The crate ships the durable-run mechanism and the trace; there is no daemon, scheduler, or watchdog that re-invokes the process after a crash — who restarts the process (a shell, io-cli, io-studio, systemd) is the caller's job, per the embeddable-library / no-daemon constraint.

### 0.6.0 known limitations

- The Linux (namespaces + seccomp) and Windows (Job Object + restricted token) native backends are compiled and unit-tested on the macOS build host but NOT live-run on real Linux/Windows hardware. A full target-triple cross-check is additionally blocked only by rusqlite's bundled-C cross toolchain (an environment limit, not a limit of the sandbox code). The portable floor is real on all three OSes, so isolation is never absent — but the native backends' runtime behaviour on their own OS is unverified here.
- macOS does not enforce address-space rlimits (RLIMIT_AS/RLIMIT_DATA — verified empirically), so the memory cap is an RSS poll-and-kill monitor (~40ms sampling), not a hard kernel limit; a very fast allocation spike could briefly exceed the cap before the monitor kills it.
- RLIMIT_NPROC is deliberately NOT applied by the portable floor — it is per-real-uid, not per-sandbox, so capping it there would throttle the operator's whole login session. Per-sandbox process-count limiting exists only in the native pid-namespace (Linux) and Job-Object (Windows) backends.
- Network is deny-by-default only. A configurable egress allow-list (letting a run reach a named host) is 0.8.0. On the portable floor and the Windows backend, "network denied" is best-effort (proxy env stripped), not a kernel boundary; Linux (net namespace) and macOS (sandbox-exec profile) deny for real.
- The portable floor is the weakest backend by design — filesystem-scoped (a fresh ephemeral workdir) and resource-capped, NOT a full syscall jail. It is the guaranteed-present minimum, not a substitute for a native backend where one exists.
- Isolation is in-process on one host using OS-native primitives and a portable floor — no container, microVM (firecracker/gVisor), or remote/multi-machine sandbox, per product.yaml (local, single-user, embeddable library).
- The Windows Job Object backend maps SandboxLimits to Job-Object fields (unit-tested) but the actual Job-Object syscall enforcement is not exercised here; on Windows the backend currently provides wall-clock capping, output capture, and kill-on-drop via the shared path, with full Job-Object enforcement to be verified when live-run.
- T08 sibling-independence test gap (accepted by owner): "a child sandbox start-failure does not take down siblings" is proven indirectly (typed Error::Sandbox start-failure unit test + run_tree's existing child-error isolation shown by the subagents suite), with no single tree+start-failure injection test, because making one child's rustc unspawnable is not reachable through the public API.

### 0.5.0 known limitations

- No execution sandbox — children still compile model-produced code directly on the host (the risk carried since 0.2.0), now multiplied by the fan-out factor. 0.5.0 bounds what the tree may touch and spend, not where code runs; per-run isolation is the very next release, 0.6.0.
- No whole-tree crash-resume. 0.5.0 reuses 0.4.0's single-pending-action persistence; a process restart does not resume an in-flight fleet. Full tree checkpointing is 0.7.0.
- Concurrent siblings share one workspace with last-write-wins — a decomposition that fans out onto overlapping files can corrupt state before 0.6.0's per-run sandbox brings real write isolation. The trace records both writes; the parent is expected to decompose to avoid collisions.
- The aggregate ceiling overshoots slightly by design: when the tree budget is exhausted mid-flight, in-flight children finish their current step before stopping, so no child is left with a half-applied edit. The small overshoot is recorded honestly in the trace rather than prevented.
- The spend ceiling is denominated in tokens as the hard, provider-agnostic ceiling; max_total_cost is an optional derived estimate only, and max_total_duration is optional wall-clock.
- No per-agent provider or model selection — the whole tree runs under the provider given at root construction (deferred, not committed for 0.5.0).
- No inter-agent coordination beyond parent<->child spawn and compose-back — no sibling messaging, shared mutable blackboard, or agent-to-agent RPC. Coordination is through the parent and the shared workspace only.
- The aggregate budget ledger is a single shared lock — deliberately the one point of serialization, adequate for one-host in-process fan-out and not tuned for throughput beyond that.
- mode is release-ready, not published: 0.5.0 is built, tested, documented, and packaged but not uploaded to crates.io; publish is deferred to the release/merge stage by owner decision, as for 0.1.0-0.4.0. cargo publish --dry-run passes and CARGO_REGISTRY_TOKEN is available.
- `Containment` field names are now a cross-repo serde contract the moment io-cli and io-studio adopt it, like `Policy` in 0.4.0; neither app has adopted it yet, so the composition value is unrealised until they do.

### 0.4.0 known limitations

- Single-file mode is not policy-enforced. A policy only applies to workspace contracts (TaskContract::workspace). Passing a non-permissive policy with a single-file contract now returns an error rather than running unenforced — this was found by the completion gate, where it had been a silent no-op, and fixing it was release-blocking. Extending enforcement to the single-file loop is outstanding.
- A refused action can still waste a run. Refusals count against the step budget (a decided trade-off), so a model that repeatedly retries a denied action is bounded by the step cap but achieves nothing. Confirmed live: with no guidance the model retried a denied read on steps 2, 4, 7 and 8 and hit StepCapReached without doing the work. The mitigation today is a TaskContract constraint telling the model not to retry refused actions, which turned the same task into Success{steps:4}. A repeated-refusal early stop is the named follow-up.
- Rules remembered before a Defer are not persisted with the pending action. They are returned on RunResult::remembered, so a caller can merge them into the policy it passes to resume_with_decision, but the crate does not do this for it — a caller that ignores the field silently loses them on resume.
- The model is not told when approve-with-changes altered its action (matching Claude Code's behaviour). The loop re-reads the workspace each step so it observes reality eventually, but it may waste a step believing it wrote a path it did not.
- The command policy gates the binary name only, not arguments. Sound today because every argv element is harness-constructed (src/verify.rs) and no model or caller output reaches it; the full argv is traced. Argument gating becomes required in 0.6.0 when plugins/MCP can supply argv.
- Which form is remembered when an approver both rewrites and remembers is the approver's choice — the crate applies exactly the rules handed to it and does not derive them from either the requested or the performed action.
- The default is permissive: a caller who passes no policy gets no enforcement. Deliberate for 0.3.0 compatibility, but it means 0.4.0 ships a boundary nobody gets unless they opt in, and neither io-cli nor io-studio has adopted it yet — the release's value is unrealised until they do.
- Policy layering is composed, not discovered: the crate merges a stack it is handed and never reads a config file. Where the shared base lives, and in what precedence, is unsettled across io-cli and io-studio.
- mode is release-ready, not published: 0.4.0 is built, tested, documented and packaged but not uploaded to crates.io; publish is deferred to the release/merge stage by owner decision, as for 0.1.0-0.3.0. cargo publish --dry-run passes and CARGO_REGISTRY_TOKEN is available.
- Execution-based verification still compiles model-produced code locally with no sandbox (sandboxes are 0.5.0), inherited from 0.2.0. The command policy constrains which binary runs, not what it may do.
- Policy glob matching compiles a regex per check and matches full relative path or basename; adequate for a handful of rules per tool call, not tuned for large rule sets.
