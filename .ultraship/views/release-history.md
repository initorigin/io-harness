### 0.16.0 known limitations

- This record was sealed on feat/0.16.0 before the crates.io upload, which follows the develop→main merge and the GitHub Release. `mode: published` states the authorised target; the release flow makes it true.

- A registered tool named after one of the git, image or document built-ins passes Toolbox validation and is then permanently unreachable. RESERVED_TOOL_NAMES still lists only the original seven, and dispatch tests every built-in arm before reaching the toolbox. Found while auditing the README against the source. Documented in CONTRACT.md rather than fixed, because extending the reserved set turns a currently-accepted registration into an Error::Config, which belongs in a release that can carry a break.

- `resume_tree` does not call record_run_policy, unlike run_tree and both flat loops, so a tree resumed under a widened policy leaves an audit that understates what was permitted. The new resume_tree_from_stored_policy is unaffected, since it reads that row back.

- `SandboxLimits::max_processes` is enforced by nothing on any platform. The doc comments claiming otherwise were corrected here; the field's behaviour was not changed.

- No seccomp filter is installed on Linux. Three doc comments claimed one and were corrected. The backend is namespaces and rlimits, and any syscall restriction is the kernel's own default under an unprivileged user namespace.

- The public-surface snapshot covers the 106 items re-exported from the crate root. Items reachable only through a public module path — io_harness::context::assemble, io_harness::tools::Workspace, the whole documents API — are public and are not individually snapshotted, so the deprecation cycle's mechanism does not yet cover them. Stated in CONTRACT.md.

- The worked-example check counts fenced blocks. It cannot distinguish a worked example from a token one, so the quality of the 106 examples rests on review rather than on the checker.

- Carried from earlier releases and documented rather than fixed: git_status uses --porcelain=v1 without -z, so a path containing a newline renders ambiguously to the model; commit idempotency across a resume rests on git's own semantics rather than a durable marker; fill_form's output has never been opened in a real PDF viewer, which needs Pdfium and therefore a system package; the Windows Job Object is still unimplemented, so containment there is the portable floor and the CPU and memory caps do not fire; pdf::read_text's catch_unwind is a no-op under a panic = "abort" profile; and no binary document fixture was written by a real application.

- The three-OS CI matrix had not run on this branch when the record was sealed. Every gate above was run on macOS. Linux and Windows are proven by the matrix on the feat→develop pull request.


### 0.15.0 known limitations

- Commit idempotency across a resume rests on git's own semantics rather than on a durable marker taken around the commit. A replayed `git_add` finds the file unmodified and stages nothing, so the replayed `git_commit` finds nothing staged and makes no commit. It is asserted by a test that replays the identical add-and-commit after a resume, and it holds — but the mechanism belongs to git, not to this crate's checkpointing, and a future git built-in that is not naturally idempotent would not inherit it.

- `git_status` uses `--porcelain=v1` without `-z`, so its output is newline-separated. A path containing a literal newline would be rendered ambiguously to the model. This is a display concern and not a boundary one — the path gate and the argv builder both handle such a path correctly, and a test asserts a path with a newline survives as one argv element — but the report the model reads would be wrong about it.

- `resume_from_stored_policy` covers the single-file and workspace loops. `resume_tree` has no stored-policy form, so a crashed agent tree still requires the caller to supply the policy.

- A viewed image rides exactly one request and is then dropped. That is deliberate — it is a tool result, not a permanent part of the conversation — but a model that needs to look again spends another step, and nothing tells it that in advance beyond the tool description.

- The crate never decodes an image. The media type comes from the file extension and the bytes are forwarded unparsed, so a corrupt file named `.png` reaches the vendor and comes back as an HTTP 400. Parsing it here would mean an image decoder in the default path of a crate that has one only behind the barcode feature.

- A run under a narrow write policy must allow `.git` or its commits are refused. The refusal is correct and traced, but the only signal is the refusal itself; there is no earlier or clearer error, and the requirement is documented rather than checked at configuration time.

- Git is local only, by design: no push, fetch, clone or remote, and no branch, merge or tag either. Commits land on the branch that is checked out. A caller who wants the agent on its own branch checks one out before starting the run.

- The live run used one provider, one model, one image and one repository. It exercises both halves end to end under a permissive policy; the refusals and their controls are covered by tests rather than by a live model.

- `fill_form` now generates real appearance streams for text fields, which closes 0.14.0's weakest claim at the level it can be closed without rasterising: the stream draws the value and the test asserts on the decoded bytes. It has still never been opened in a real PDF viewer, because proving that means Pdfium, which is a per-OS binary this release's no-system-package constraint forbids. Checkboxes and radios keep their existing state-selection behaviour; choice fields are drawn as plain text, single-line and left-aligned, and quadding, multiline and comb fields are not honoured.

- MCP images are attached only when the tool did not report an error, on the grounds that an image arriving with a failure is not something anyone asked to see. That is a judgement, and a server that reports an error alongside a diagnostic screenshot loses the screenshot.

- `CompletionRequest` gaining a field is source-breaking for a caller using an exhaustive struct literal. Under 0.x that is a minor bump, which is what this is, and the type now derives `Default` and documents `..Default::default()`, so this is the last time a field addition breaks it.

### 0.11.0 known limitations

- The record is sealed before the crates.io upload, which follows the two merges and the GitHub Release. `mode: published` states the authorized target.

- Stall detection is a heuristic over two signals, not a proof. It reads whether a write changed the file's bytes and whether a tool call repeated. An agent making real progress the harness cannot see — reasoning, or work inside a registered tool whose effects are outside the workspace — could in principle be flagged, which is why the window is configurable and can be set to 0.

- The stall signature is the joined tool-call text, so two calls that differ only in an irrelevant argument read as different work and reset nothing. An agent that varies a padding argument while achieving nothing would not be caught.

- `with_stall_policy` is inert for a single-file run, which has one tool and one file. Documented on the builder rather than silently accepted.

- The request deadline is 600s by default. Long enough that no realistic single completion reaches it — a full 8192-token stream at a sluggish 15 tokens/second is about nine minutes — but a caller running a slower model or a much longer output should raise it. A hung socket is caught by any finite deadline, so the default is deliberately generous rather than tight.

- Backoff is deterministic, with no jitter. Many clients retrying in lockstep after a shared outage would synchronise; jitter needs a randomness dependency this release does not take, and would make the wait assertions untestable without loosening them until they assert nothing.

- Falling over swaps the model mid-run and the harness cannot see whether the replacement is as capable, as well tuned, or even the same size. The provider that answered is recorded per step so an operator can tell, but nothing verifies equivalence, and a run that fell over may behave differently from one that did not.

- Nothing tracks a provider's health across runs. A provider that failed every call last run starts the next one trusted; a circuit breaker needs a store surface and an expiry policy and is a different feature from surviving the failure in front of you.

- Honouring `Retry-After` is not rate-limit management. There is no token bucket and no quota model, so a run that is being throttled will keep asking and keep waiting.

- `Retry-After` handles delta-seconds and IMF-fixdate only. RFC 850 and asctime dates degrade to "no hint" rather than to a wrong wait, marked `ponytail:` with the upgrade path named.

- The malformed kind fires only when NOTHING in a stream parsed. A provider that emits a valid but truncated response — half the tool call, then a clean end — is still `Ok`, and looks to the loop like a model that changed its mind.

- Windows containment is still the portable floor with a wall-clock cap only, and `Backend::WindowsJobObject` remains a public variant nothing constructs on the enforcement path. Unchanged since 0.9.1; it needs a `windows-sys` binding and its own release.

- Every Windows claim in this record rests on CI run 30202128038. Nobody on this project has a Windows machine, and this release is the second time in three releases that CI found a real Windows-specific behaviour nothing local could see.

The portable floor is real on all three OSes, so isolation is never absent — but the native backends' runtime behaviour on their own OS is unverified here.
- macOS does not enforce address-space rlimits (RLIMIT_AS/RLIMIT_DATA — verified empirically), so the memory cap is an RSS poll-and-kill monitor (~40ms sampling), not a hard kernel limit; a very fast allocation spike could briefly exceed the cap before the monitor kills it.
- RLIMIT_NPROC is deliberately NOT applied by the portable floor — it is per-real-uid, not per-sandbox, so capping it there would throttle the operator's whole login session. Per-sandbox process-count limiting exists only in the native pid-namespace (Linux) and Job-Object (Windows) backends.
- Network is deny-by-default only. A configurable egress allow-list (letting a run reach a named host) is 0.8.0. On the portable floor and the Windows backend, "network denied" is best-effort (proxy env stripped), not a kernel boundary; Linux (net namespace) and macOS (sandbox-exec profile) deny for real.
- The portable floor is the weakest backend by design — filesystem-scoped (a fresh ephemeral workdir) and resource-capped, NOT a full syscall jail. It is the guaranteed-present minimum, not a substitute for a native backend where one exists.
- Isolation is in-process on one host using OS-native primitives and a portable floor — no container, microVM (firecracker/gVisor), or remote/multi-machine sandbox, per product.yaml (local, single-user, embeddable library).
- The Windows Job Object backend maps SandboxLimits to Job-Object fields (unit-tested) but the actual Job-Object syscall enforcement is not exercised here; on Windows the backend currently provides wall-clock capping, output capture, and kill-on-drop via the shared path, with full Job-Object enforcement to be verified when live-run.
- T08 sibling-independence test gap (accepted by owner): "a child sandbox start-failure does not take down siblings" is proven indirectly (typed Error::Sandbox start-failure unit test + run_tree's existing child-error isolation shown by the subagents suite), with no single tree+start-failure injection test, because making one child's rustc unspawnable is not reachable through the public API.

### 0.5.0 known limitations

- No execution sandbox — children still compile model-produced code directly on the host (the risk carried since 0.2.0), now multiplied by the fan-out factor. 0.5.0 bounds what the tree may touch and spend, not where code runs; per-run isolation is the very next release, 0.6.0.
- No whole-tree crash-resume. 0.5.0 reuses 0.4.0's single-pending-action persistence; a process restart does not resume an in-flight fleet. Full tree checkpointing is 0.7.0.
- Concurrent siblings share one workspace with last-write-wins — a decomposition that fans out onto overlapping files can corrupt state before 0.6.0's per-run sandbox brings real write isolation. The trace records both writes; the parent is expected to decompose to avoid collisions.
- The aggregate ceiling overshoots slightly by design: when the tree budget is exhausted mid-flight, in-flight children finish their current step before stopping, so no child is left with a half-applied edit. The small overshoot is recorded honestly in the trace rather than prevented.
- The spend ceiling is denominated in tokens as the hard, provider-agnostic ceiling; max_total_cost is an optional derived estimate only, and max_total_duration is optional wall-clock.
- No per-agent provider or model selection — the whole tree runs under the provider given at root construction (deferred, not committed for 0.5.0).
- No inter-agent coordination beyond parent<->child spawn and compose-back — no sibling messaging, shared mutable blackboard, or agent-to-agent RPC. Coordination is through the parent and the shared workspace only.
- The aggregate budget ledger is a single shared lock — deliberately the one point of serialization, adequate for one-host in-process fan-out and not tuned for throughput beyond that.
- mode is release-ready, not published: 0.5.0 is built, tested, documented, and packaged but not uploaded to crates.io; publish is deferred to the release/merge stage by owner decision, as for 0.1.0-0.4.0. cargo publish --dry-run passes and CARGO_REGISTRY_TOKEN is available.
- `Containment` field names are now a cross-repo serde contract the moment io-cli and io-studio adopt it, like `Policy` in 0.4.0; neither app has adopted it yet, so the composition value is unrealised until they do.

### 0.4.0 known limitations

- Single-file mode is not policy-enforced. A policy only applies to workspace contracts (TaskContract::workspace). Passing a non-permissive policy with a single-file contract now returns an error rather than running unenforced — this was found by the completion gate, where it had been a silent no-op, and fixing it was release-blocking. Extending enforcement to the single-file loop is outstanding.
- A refused action can still waste a run. Refusals count against the step budget (a decided trade-off), so a model that repeatedly retries a denied action is bounded by the step cap but achieves nothing. Confirmed live: with no guidance the model retried a denied read on steps 2, 4, 7 and 8 and hit StepCapReached without doing the work. The mitigation today is a TaskContract constraint telling the model not to retry refused actions, which turned the same task into Success{steps:4}. A repeated-refusal early stop is the named follow-up.
- Rules remembered before a Defer are not persisted with the pending action. They are returned on RunResult::remembered, so a caller can merge them into the policy it passes to resume_with_decision, but the crate does not do this for it — a caller that ignores the field silently loses them on resume.
- The model is not told when approve-with-changes altered its action (matching Claude Code's behaviour). The loop re-reads the workspace each step so it observes reality eventually, but it may waste a step believing it wrote a path it did not.
- The command policy gates the binary name only, not arguments. Sound today because every argv element is harness-constructed (src/verify.rs) and no model or caller output reaches it; the full argv is traced. Argument gating becomes required in 0.6.0 when plugins/MCP can supply argv.
- Which form is remembered when an approver both rewrites and remembers is the approver's choice — the crate applies exactly the rules handed to it and does not derive them from either the requested or the performed action.
- The default is permissive: a caller who passes no policy gets no enforcement. Deliberate for 0.3.0 compatibility, but it means 0.4.0 ships a boundary nobody gets unless they opt in, and neither io-cli nor io-studio has adopted it yet — the release's value is unrealised until they do.
- Policy layering is composed, not discovered: the crate merges a stack it is handed and never reads a config file. Where the shared base lives, and in what precedence, is unsettled across io-cli and io-studio.
- mode is release-ready, not published: 0.4.0 is built, tested, documented and packaged but not uploaded to crates.io; publish is deferred to the release/merge stage by owner decision, as for 0.1.0-0.3.0. cargo publish --dry-run passes and CARGO_REGISTRY_TOKEN is available.
- Execution-based verification still compiles model-produced code locally with no sandbox (sandboxes are 0.5.0), inherited from 0.2.0. The command policy constrains which binary runs, not what it may do.
- Policy glob matching compiles a regex per check and matches full relative path or basename; adequate for a handful of rules per tool call, not tuned for large rule sets.
