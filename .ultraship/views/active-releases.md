# Active releases

## io-harness 0.12.0

**Execution state:** DEVELOPING
**Release fit:** probable
**Target mode:** published
**Outcome:** A developer embedding the harness can watch a run as it happens, and a developer measuring the harness can prove a change made it better. Neither is possible today, and the audit for this release found the gaps are wider than the roadmap assumed.
Watching is not supported at all. `src/lib.rs:214-258` exports no observer, no callback, no channel and no subscription of any kind; the full grep for `broadcast|mpsc|watch|Sender| Receiver|subscribe|on_event|dyn Fn` across `src/` returns three hits, all of them predicates or a test-only fixture. The only way to see a run in flight is to open the SQLite file with a second connection and poll it. That works only by accident of `Store::checkpoint_step` (`src/state.rs:1175`) committing each step in its own short transaction, and it is not a contract: `Store::open` (`src/state.rs:644`) is a bare `Connection::open` that sets neither `journal_mode=WAL` nor `busy_timeout`, so a second reader either blocks the writer or aborts on contention unless it opens the file first and sets both pragmas itself, and it must guess at the schema — which is precisely the coupling this release exists to remove.
Measuring has no surface either. Nothing in the crate records a provider response, so a case cannot be re-run against what the model said last time. `CompletionRequest`, `CompletionResponse`, `ToolCall`, `ToolSpec` and `Usage` (`src/provider/mod.rs:102-156`) carry no serde derives at all, so there is no format to record into. What the trace does keep is lossy in three ways: `CompletionResponse.text` is discarded entirely whenever `tool_calls` is non-empty (`src/run.rs:892-905`), `Usage.prompt_tokens` and `completion_tokens` are dropped in favour of `total_tokens` alone (`src/run.rs:714`), and tool calls are flattened to `format!("{name}:{args}")` joined with `" | "` (`src/run.rs:909`, `:1359`), which a `|` inside an argument corrupts.
And a run is not deterministic even given the same responses. `src/context.rs:545-549` renders every memory note as `"- {key}: {value}  (run {run_id}, step {step})"`, and `run_id` is a SQLite `AUTOINCREMENT`, so the same case run twice in one store sends the model **different prompt bytes** — and that string is persisted into `steps.prompt`. Sub-agent results are collected by `buffer_unordered` (`src/run.rs:1401-1408`) in completion order rather than spawn order, so `steps.decision`, `steps.result` and the ordering of `runs.id`, `spawns.child_run_id` and `agent_events` all vary between identical runs. Cross-run `memory` means a second run reads what the first wrote. And `Store::elapsed_secs` (`src/state.rs:1249`) measures real wall-clock from the database, so whether a run ends `Success` or `TimeBudgetExceeded` can differ on a slow machine.
The per-run record does not exist. `runs` holds `goal, file, outcome, provider, parent_run_id, depth, status, started_at` (`src/state.rs:655-661` plus its ALTERs) — no end timestamp anywhere in the schema, so a finished run's latency is not recorded and not derivable; `elapsed_secs` is live and keeps growing after `finish_run`. Success is an unvalidated free-text string, of which eleven are written against nine `RunOutcome` variants. Steps are only reachable as `MAX(step)`, which is not a step count because retry rows reuse the step number (`src/run.rs:2359`, `:2377`, `:2390`). Spend is tokens; cost telemetry does not exist, and `Containment.max_total_cost` and `max_total_duration` (`src/containment.rs:37,40`) are declared, defaulted, serde-roundtripped in a test, and **never read** — a caller can set a tree-wide duration ceiling on a 24-hour run and it does nothing.
After this release: a caller registers an observer and is called as the run happens, for every kind of thing the trace already records, with each event serialisable so a host process can forward it to a user interface written in another language without hand-writing a mapping. Cancelling a run is something the caller asks for rather than something it achieves by dropping a future. A recorded provider replays a case so that two runs over the same recording produce the same trace, with the sources of variance either removed or documented as excluded from the comparison. And a finished run yields one record carrying whether it succeeded, how many steps it took, what it spent, and how long it took — from the crate's own API, without a consumer writing SQL against a schema the crate never promised.
