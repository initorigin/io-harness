# Active releases

## io-harness 0.42.0

**Execution state:** DEVELOPING
**Release fit:** probable
**Target mode:** published
**Outcome:** Leave a run unattended and have the decisions it meets answered, checked and — when nobody should answer them — parked for a human, without writing a line of Rust for any of it.
Three things a run stops needing a present human for, and one thing a reviewer stops being lied to about.
**A model can be installed as the `Approver`.** Today the three built-in approvers are `ApproveAll`, `DenyAll` and `StdinApprover` (`src/approve.rs:261`, `:293`, `:328`): wave everything through, refuse everything, or block on a terminal that is not there. An unattended job therefore either runs with its grey tier fully open or dies at the first `Effect::Ask`. 0.42.0 adds `ModelApprover`, the mirror of 0.34.0's `ModelReviewer`: it reads the pending act, what it targets, the bytes a write would land, **the rule and the layer that flagged it**, and the run's goal — then approves, denies with a reason the model under it will read, or defers. Deferring is the escalation, and it already means the right thing: the pending action is persisted, the run stops with `RunOutcome::AwaitingApproval`, the process may exit, and the human who reads the trace tomorrow answers it with `resume_with_decision`. No new `Decision` variant is invented for something the crate already does.
The rule and the layer are the reason this is worth having rather than a novelty. An approver that sees only `Act::Write` on `src/main.rs` is guessing; one that sees "the `ops-baseline` layer's `deny_write src/main.rs` did not fire, the app layer's `*.rs` Ask tier did" is answering the question an operator actually asked. `Policy::explain` has carried `Verdict { effect, rule, layer }` since 0.13.0 (`src/policy.rs:274`) and the approver has never been shown it.
**A model must never approve its own call.** `Verification::Review` already refuses a reviewing model that is the model under review, before a request is built (`preflight_review_and_routing`, `src/run.rs:2843`). The same refusal now covers approval, from the same place and with the same escape hatch stated in the caller's own code: a `ModelApprover` whose model is the run's model is an `Error::Config` at run start — zero calls to either provider — unless the caller wrote `allow_self_approval(true)` and meant it.
**An operator attaches a check to a named point in the tool lifecycle from `io.toml`.** A `[[hook]]` today is an `Observer` (0.28.0): it names events by their wire tags, and the strongest thing it can do is `on_failure = "cancel"`, which is honoured at the **next step boundary** — after the tool it objected to has already run. So "no `exec` of `terraform` in this repository, ever, whatever the agent decides" is not expressible as a table entry; it is a Rust `Approver` impl an operator has to compile in. 0.42.0 gives a hook table the key `at`, whose one value in this release is `before_tool`, and an optional `tools` filter. Such a hook is spawned with the pending call on its stdin **before the call executes**, in the serial policy phase all three dispatch sites already share (`prepare_read`, `src/run.rs:7203`). A non-zero exit refuses that one call: nothing runs, the hook's own first line of stdout becomes the reason the model reads, and the run adapts rather than dying — the same shape as a policy deny. An operator who wants the wall instead writes `on_failure = "cancel"`.
That check obeys the trust rule without exception. `[[hook]]` is refused in a project-scoped `io.toml` because a hook runs an argv a clone delivered, and a hook that can stop a tool is strictly more dangerous than one that appends a log line, so `at` inherits the refusal rather than reopening the question.
**And the review criterion reads the change instead of the outcome.** `Verification::Review` hands the reviewer `written_files` (`src/run.rs:3031`): every file the run wrote, with its contents **as they stand now**. That is the outcome, and a reviewer of a code change reads the change. A rubric like "no public item lost its doc comment" cannot be answered from a file that no longer contains the comment — the deletion is invisible, because what was deleted is not in the text. The store has held the answer since 0.28.0: `snapshots` keeps each file's contents from before the run first wrote it, for the rewind. 0.42.0 spends nothing new to reach it. A `ModelReviewer` is now handed a `ChangeReview` carrying, per file, what was there before and what is there now; a file the run created carries no before, a file it never touched is not in the list at all, and a file whose previous contents the snapshot cap did not keep says so rather than pretending it was empty.
