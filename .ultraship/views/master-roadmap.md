# Master roadmap

## io-harness

| Version | Outcome | Detail | Status |
| --- | --- | --- | --- |
| 0.1.0 | A developer embeds the crate, hands it one file-edit task contract, and the harness runs the loop (observe, reason, act, verify, stop) with the filesystem tool and the OpenRouter provider; the verification layer confirms the file meets the spec and the run stops on success or a step cap. | specified | released |
| 0.2.0 | A developer runs a longer, multi-step task and can trust it: step, time, and cost budgets are enforced, failed steps are retried or recovered, and a full trace plus rusqlite state make the run auditable and resumable. Verification is execution-based — the gate compiles and/or runs a test against the produced artifact, so a task cannot pass with a substring stub (0.1.0 live run showed FileContains is trivially gamed; see iterations/US-IO-HARNESS-0.2.0-I01). | specified | released |
| 0.3.0 | A developer runs a task that greps and finds across a repository and edits several files, choosing OpenRouter, Anthropic, or OpenAI as the provider. | specified | released |
| 0.4.0 | A developer runs an agent on sensitive work under an explicit permission policy: deny-by-default path rules decide which files it may read and write, and a command policy decides which binaries verification may execute. Out-of-policy actions are refused rather than performed, and actions marked sensitive stop for a human decision before they happen — either through an Approver the caller supplies in-process, or by pausing the run, persisting the pending action, and resuming once a decision arrives. Every refusal and every approve/deny is in the rusqlite trace. The policy is serde-serializable and composes in layers, so io-cli and io-studio each keep their own config over a shared base instead of each building its own permission model. | specified | released |
| 0.5.0 | A developer hands the harness one large task and a parent agent decomposes it, spawning sub-agents on demand — up to 100+ concurrently — each running its own observe/reason/act/ verify/stop loop over a shared workspace and a shared trace, with results composed back so the parent continues from what the children produced. Children can nest (spawn their own children) to a bounded depth. The 0.4.0 policy becomes a containment boundary: a child inherits its parent's policy and can only narrow it — it can never grant itself read, write, or execute the parent lacks — and the whole tree runs under one aggregate spend ceiling (agent count, tokens, cost, time) that no spawned task contract can raise. Every spawn, every parent/child edge, and every draw against the shared budget is in the rusqlite trace as one auditable graph. | specified | released |
| 0.6.0 | A developer runs a task whose generated code executes inside an ephemeral local sandbox that is created, run, captured, and destroyed per run, so execution-based verification and any agent-run command no longer compile and run model-produced code directly on the host — closing the "compiles locally, no isolation" limitation carried since 0.2.0 and made sharper by 0.5.0's many concurrent agents. The sandbox is both OS-native and OS-neutral: a single `Sandbox` trait with a real native backend per platform (macOS sandbox-exec, Linux namespaces+seccomp, Windows Job Objects) over a portable floor (ephemeral tempdir, resource caps, network denied) that compiles and runs on all three, so the same harness isolates code the same way on mac, linux, and windows. | specified | released |
| 0.7.0 | A developer starts a task and walks away: the harness runs unattended for a long horizon (24h+) with no user input, durably checkpointing after every completed step so a crash or full restart resumes the whole agent tree exactly where it stopped — completed steps are not re-run, the 0.5.0 aggregate budget is not double-charged, and an irreversible action already taken is not taken twice. A policy-required approval (0.4.0) pauses the whole tree, persists the pending action, and resumes on the human decision even across a restart in between. Ephemeral 0.6.0 sandboxes die with the process and are re-created on resume; an exec in flight at crash time is replayed idempotently. Proven by a real kill-9-then-resume-to-completion crash test plus a time-scaled long unattended run; a literal 24h wall-clock run is noted, not gated on. | specified | released |
| 0.8.0 | A developer points the harness at MCP servers and the agent uses their tools alongside the built-ins, in the same observe/reason/act/verify/stop loop — the crate becomes extensible without a fork. Because MCP servers are the first callers that can dial an arbitrary host, network egress stops being ungoverned: the 0.4.0 permission model gains a network act, so outbound calls (the provider, an HTTP MCP server, an MCP tool's own reach) are deny-by-default, layered, and either allowed, refused, or paused for a human decision by the same policy that already governs read, write, and exec. Refusals and decisions are in the rusqlite trace, a 0.5.0 child can only narrow its parent's network rules, and a network approval survives a restart under 0.7.0 durable pause. | specified | released |
| 0.8.1 | An operator can trust that a passing execution gate was not defeated by the file it verified. The subject file can no longer shadow what the criterion names, so the recorded bypass — a `#[macro_export] macro_rules! assert` making `assert!(false, "this gate can never pass")` report ok — fails, and so does the same attack through `WorkspaceTestPasses`. The crate documents plainly what a passing gate does and does not prove, so io-cli and io-studio stop inheriting a guarantee the gate never made. See iterations/US-IO-HARNESS-0.8.0-I01. | specified | released |
| 0.9.0 | A developer extends the harness in-process without MCP: their own typed tools registered against a public tool trait, compiled into their binary, offered to the model beside the built-ins and governed by the same 0.4.0/0.8.0 policy and trace; and skills — instruction files discovered from a directory, whose body shapes how the agent approaches a class of task. io-cli and io-studio each add their own capabilities and behaviour over the shared engine. No dynamic loading and no plugin ABI — out-of-process extension is what 0.8.0's MCP client is for. Skills carry instructions, not code. | specified | released |
| 0.9.1 | A developer on Linux or Windows gets the isolation and verification the crate has claimed since 0.3.0 and 0.6.0, or is told plainly that they do not. 0.9.0 added the repository's first CI matrix and it immediately disproved three standing claims: on Linux the execution-based verification gate does not work at all (7 `verify::tests` failures, `passes_guarded` returning false) and the sandbox CPU and memory caps never fire (`cap_hit: None` where `Some(Cpu)` is expected); on Windows no Job Object is ever created, so containment is the portable floor and the suite hangs rather than being killed by a cap. 0.9.0 corrected the false `Backend::WindowsJobObject` label and documented the gap; this release closes it — the Linux verify and cap failures are root-caused and fixed, the Windows suite terminates, and the Windows native backend is either implemented against the Win32 job-object API or formally declared unsupported-for-containment in the roadmap rather than left as an unfulfilled promise. The matrix stays green on all three platforms afterwards, which is what makes 0.6.0's "the same harness isolates code the same way on mac, linux, and windows" a true sentence. | specified | released |
| 0.10.0 | A developer runs a long task and the agent's context stays relevant instead of merely growing. What the model sees each turn is assembled to fit a stated share of the token budget: superseded observations are compacted, an observation invalidated by a later write is re-read rather than trusted, and each tool result is bounded where it enters the context rather than where it enters the trace. The agent also keeps durable memory — facts and decisions it writes deliberately and recalls on a later run over the same workspace — so a second run does not rediscover what the first established. Closes the context-construction and state-and-memory gaps; see iterations/US-IO-HARNESS-0.9.0-I01. | specified | released |
| 0.11.0 | A developer's long unattended run survives the failures that end runs today, not just the crashes 0.7.0 covers. A provider that is down, rate-limited, or returning garbage falls back to another configured provider instead of escalating; an agent spending steps without changing the workspace is detected as stalled and replanned once rather than burning to the step cap; and the escalation path distinguishes a retryable transport failure from a terminal one so a caller learns which happened. Every fallback, stall, and replan is in the trace. | specified | released |
| 0.12.0 | A developer watching a run sees it as it happens, and a developer measuring the harness can. An embedding application registers an observer and is called as the run happens — steps, tool calls, approvals, refusals, spend draws, retries, fallbacks, stalls, outcomes — instead of polling the store, and every event serialises, so a host process can forward it to a UI in another language without hand-writing a mapping. The same release makes a run measurable: a recorded provider replays a case so it runs identically twice, and a per-run outcome record carries success, steps, spend, and latency, none of which the store holds today. Closes the observability and evaluation gaps and completes the twelve pillars; see iterations/US-IO-HARNESS-0.9.0-I01, whose stated dependency direction is corrected here — the harness defines these surfaces on its own contract, and the applications are built against them, not the reverse. | specified | released |
| 0.13.0 | A developer who resumes an interrupted run gets the run they had, not a similar one. Resume today restores only the durable half — the step it reached, what it spent, how long it has been alive — and silently substitutes the rest. Two things go missing, and both are the same defect. The permission boundary: `resume` and `resume_observed` hardcode `Policy::permissive()` and `ApproveAll` for every workspace run (src/run.rs:334-356), so a caller who started under a restrictive policy through `run_with` and resumes after a crash gets an agent with no boundary, and no policy-preserving general resume exists to reach for — `resume_with_decision` takes a policy but demands a `request_id` and a pending `Decision`, so it only serves a run that paused for approval. The crate states the opposite principle 60 lines earlier at src/run.rs:270-279, where single-file mode refuses a policy loudly precisely so a caller never believes a boundary is enforced when nothing is checking. And the assembled half: the observation ledger the 0.10.0 context assembler builds is in memory only, built fresh at src/run.rs:1242 and :1821 after the resume step is already known, so a resumed workspace or sub-agent run re-derives its context from the workspace and asks the model a different question than the process before it would have. After this release a resumed run carries the policy it was started under and the context it had: `resume` gains a policy-bearing form, a run that was started under a policy cannot be silently resumed without one, the ledger is durable and restored, and a recorded case replays identically across an interruption in every loop rather than only the single-file one. Pulled ahead of documents because a boundary a caller believes is enforced and is not is worth more than breadth, and because both halves live in the same functions — worth touching resume once, not twice. The ledger half was found by 0.12.0's replay work and recorded in iterations/US-IO-HARNESS-0.12.0-I01, where 0.12.0 shipped the honest boundary instead: a replay that cannot reproduce a request refuses loudly rather than answering from the wrong recording. | specified | released |
| 0.14.0 | A developer runs a task over real documents. The agent reads and edits a real spreadsheet keeping the rest of the workbook intact, generates and reads Word documents, generates PDFs and extracts their text, watermarks a PDF and fills its form fields, and decodes a barcode or QR code off a page — under the same path policy, sandboxing and verification that govern source edits. That last clause is the release, not a qualifier: a document tool is not a registered `Tool`, because a registered tool is authorised once by name and the crate is explicit (README) that the policy "governs whether it is called; it does not govern what it does once running — no path scoping". A capability whose whole job is reading and writing workspace files cannot sit outside the path rules, so document tools are dispatched as built-ins with a real per-path gate, over new byte-level policy-checked workspace IO, and verified by a document-aware criterion — none of the seven existing `Verification` variants can check a `.docx`, since `FileContains` on one matches against zip bytes. OCR is cut from the roadmap entirely, not deferred to a later version — the owner's decision, 2026-07-27. It appears in no planned release. The evidence supported it: Tesseract binds a C++ library needing vcpkg on the Windows runner, and the pure-Rust alternative requires MSRV 1.89 against this crate's 1.88 floor, fetches models over the network at runtime, and reads Latin script only. If it returns it will be as a new roadmap entry argued on its own merits. PowerPoint is cut for writing and kept for reading, same decision, refined the same day. Authoring does not exist in Rust at a quality worth shipping — the one credible crate is a 46-star, single-maintainer, pre-0.3 project. Extracting the text of a deck is easy and several maintained pure-Rust extractors do it, so the read half stays. Word gets read-and-generate rather than in-place editing, for a separate reason: the mature crate's round trip silently drops OOXML it does not model, which for an agent editing someone's real document is data loss, so "edit a Word file in place" is not claimed. | specified | released |
| 0.15.0 | A developer hands the agent an image alongside the task and the harness passes it through to any provider whose model accepts one, and the agent works a real git repository — reading history, staging, and committing its own work — so a run ends as reviewable version control rather than loose file edits. Image work here means passthrough to a provider that accepts images. It does not mean OCR: OCR is off the roadmap by the owner's decision of 2026-07-27 and is not to be folded in here on the grounds that this is the image release. Video is cut from the roadmap entirely, not deferred — the owner's decision, 2026-07-27, and it appears in no planned release. The evidence supported it: the Anthropic Messages API and the OpenAI Chat Completions API both accept images and no video at all, and OpenRouter, the only one of the three carrying a `video_url` content part, states that support varies by model and gives no way to ask which. "Passthrough to any provider whose model accepts it" would have meant one provider out of three and no way to know when. If video returns it will be as a new roadmap entry argued on its own merits, when more than one provider takes it. Git is shelled out to the `git` binary rather than bound through a library — the owner's decision after weighing `git2` (libgit2's C, vendored) and `gix` (pure Rust, but its own crate-status has `[ ] add and remove entries`, so staging does not exist). That choice is what shapes the release. `ExecGuard::check` (src/verify.rs:248) enforces only the program name and records argv without checking it, so `Act::Exec("git")` cannot tell `git log` from `git push --force`. Git therefore ships as named built-ins that each construct their own fixed argv, with the model naming paths and never arguments: the destructive and networked surface is unreachable by construction rather than excluded by an allowlist. Two carried-over defects ride along by the owner's decision: the 0.13.0 resume-from-stored- policy gap, which matters more here because this release makes the agent take irreversible commits under a policy, and 0.14.0's `fill_form`, which sets `/NeedAppearances` instead of generating appearance streams. | specified | released |
| 0.16.0 | A developer arriving at the crate cold can tell what it does and start using it, and a developer depending on it knows what may change. The README becomes a landing page rather than a release history — one description, a quickstart above the fold, badges, the MSRV, and what the harness does today instead of what each version added — with the per-capability depth moved into guide pages under docs/ so nothing is lost. Every public item carries a worked example, each breaking change between 0.x minors is called out in the changelog with a migration note, and renamed or removed items go through a deprecation cycle instead of vanishing. The crate stays pre-1.0, so a minor may still break — what an external Rust developer can rely on is that the break is documented and survivable, not that it will not happen. The documentation rewrite lands here rather than earlier because it should describe a finished twelve-pillar harness once, not be redrafted after each pillar; 0.12.0 corrects only the README's factual errors, which are a different problem from its structure. Three things follow from taking that seriously rather than treating it as a writing task. The crate root is documentation too, and it is the one an external developer actually lands on — docs.rs opens on `src/lib.rs`, not the README. It carries the same defect in a worse place: 230 lines of "v0.2 adds", "v0.4 adds", "v0.8 adds", with v0.3 arriving after v0.14 and v0.10 through v0.13 absent entirely. It gets the same treatment as the README, from the same source of truth, so the two cannot drift apart. "Every public item carries a worked example" is a claim that decays the moment it is made unless something checks it. The release ships the check: a test that enumerates the public surface re-exported from `lib.rs` and fails on any item whose docs carry no fenced example. `cargo test --doc` already compiles every example that exists, so an example cannot rot into a lie; what is missing is the part that notices when one was never written. A deprecation cycle needs a mechanism, not a promise. The public surface is snapshotted to a checked-in file and compared by a test, so removing or renaming an item fails the build until someone updates the snapshot deliberately — which is the moment the `#[deprecated]` attribute and the changelog migration note get written, rather than a moment nobody notices. One code change rides along, because documenting an incoherent surface is worse than fixing it: `resume_tree` still has no stored-policy form, so the three resume loops disagree about whether a run can be resumed under the policy it was started with. It ships as a new named function, never an added parameter. | specified | released |
| 0.16.1 | A reader who reaches the end of the README learns which initorigin products actually exist and which they can go and look at, instead of being handed five repository links of which four are private and two name products that have not been built. 0.16.0 made the README a landing page and this is the one table it left as an aspiration rather than a fact: `io-eval` and `website` are listed as if they were shipped things, and `io-cli` and `io-studio` are linked to repositories that return 404 to everyone but their owner. The table now lists the three products the crate is actually for, states each one's status, and carries a link only for the one a reader can open. A contributor copying `.env.example` also stops being told to obtain a crates.io publish token. Publishing is the maintainer's step, not a prerequisite for running the suite, and a template that asks for a credential nobody needs teaches the wrong thing about what the project requires. Nothing a caller wrote against 0.16.0 changes. No public item is added, renamed, or removed and no behaviour differs; this is documentation correctness, which for a crate whose whole 0.16.0 thesis was "the documented public contract" is the same kind of defect as a wrong return value. | specified | released |
| 0.16.2 | A developer who follows the crates.io link to the API reference reaches a rendered page instead of a build-failure notice. docs.rs has no documentation for either 0.16.0 or 0.16.1: both fail to compile there because the crate root enables the nightly `doc_auto_cfg` feature, which Rust removed in 1.92.0 and merged into `doc_cfg`. docs.rs builds on nightly, so the failure appears only there — every stable `cargo doc` in CI and on a contributor's machine compiled it without a warning, which is why two releases shipped with it. After this release, `docs.rs/io-harness` renders the whole surface, with every item behind `documents`, `media`, or a per-format feature labelled with the feature it needs, which is what the gate was there to do in the first place. 0.16.0 and 0.16.1 stay unbuildable — a published version's sources cannot be changed — so this is the first version of the 0.16 line with a page. Nothing a caller wrote against 0.16.1 changes. The one edited line is inside `cfg_attr(docsrs, ...)`, reached only under a cfg that docs.rs sets and nothing else does. | specified | released |
| 0.17.0 | A developer points the harness at a project in any language and it works. The agent can run that project's own toolchain — `cargo test`, `npm install`, `go build`, `pytest`, `dotnet test` — through a fixed-argv `exec` tool authorized by the same `Act::Exec` check as every other tool, and it can change a file by replacing an exact string rather than rewriting the whole thing. Verification stops being Rust-shaped: a criterion can run any command and assert its exit status, or a run can declare no criterion at all and stop when the agent is done, which is what makes an open-ended task expressible for the first time. The harness also tells the agent what kind of project it is in. A marker file — `Cargo.toml`, `package.json` beside its lockfile, `go.mod`, `pyproject.toml`, `pom.xml`, and the rest — maps to that ecosystem's default build, test, lint, and format commands, shipped as data and overridable by the operator, so the agent stops spending turns guessing whether to run `npm` or `pnpm`. This is where "any task" stops being a claim about the vision and becomes a property of the code. Before it, an agent asked to fix a deployment or build an application had no way to run anything and no way to express what done meant. Two breaks ride along, both permitted below 1.0 and both carrying a deprecation cycle and a migration note: `Verification` gains variants and its Rust-specific ones become sugar over the general form. `RESERVED_TOOL_NAMES` is corrected in the same release, because dispatch is already being edited and a registered tool named after a git, image, or document built-in is currently accepted by validation and then permanently unreachable. | specified | released |
| 0.18.0 | An operator can answer "what did that run cost, and which model spent it" from the trace alone. Every provider call is recorded on its own row with the model that served it, its input, output, cache-read, cache-write, and reasoning tokens, its API latency and time to first token, and its finish reason — so a step that retried once and then fell back is three rows on three models rather than one collapsed integer. Edits record lines added and removed. Provider server-tool requests are counted alongside tokens, because search is billed per request and a token-only schema silently under-reports money. Cost is derived, never stored. Prices live in a data table the operator can correct, and correcting one repairs the whole history — which is the property that makes a stored dollar figure the wrong thing to keep. The crate ships grouped raw rows (by model, by day, by run) and stops there: streaks, favourite models, heat maps, and every other rendering are the consuming app's decision, not the harness's. Before this, the model identifier was recorded nowhere at all, cache tokens were not parsed, no provider call was timed, and `Containment::max_total_cost` was documented inert. None of the numbers an operator actually asks for could be produced at any cost. Two breaks. `Usage` gains fields, which breaks struct-literal construction — the type already documents `..Default::default()` as the forward-compatible way to build it. And the three Rust-specific `Verification` variants deprecated in 0.17.0 are removed here, the minimum cycle the crate's contract allows, leaving one execution path instead of two. The changelog note has to say plainly that a consumer upgrading 0.16.2 straight to 0.18.0 meets the removal with no intervening warning, because that is the cost of the short cycle and a reader who upgraded one minor at a time is not the only reader. | specified | released |
| 0.19.0 | An operator configures the harness in a file instead of in Rust, and io-cli and io-studio read the same file rather than inventing two formats that would have to be reconciled later. Defaults, a user scope, a committed project scope, and a gitignored local scope merge in that order, with environment and file substitution, so a project can set a boundary its collaborators inherit and an individual can override it without editing a shared file. The file is a projection onto the typed API, never a parallel path: it produces a `Policy`, a `SandboxConfig`, a `TaskContract`, and the toolchain and pricing tables added by the two previous releases. The typed API stays the authority — configuration is the ergonomic front end to it, and a test asserts every key reaches a typed field. It lands third on purpose. Its schema is determined by what exists, and writing it before command execution, general verification, and the accounting tables would have meant writing it twice. | outline | planned |
| 0.20.0 | A run stops being one-shot. An operator opens a session, sends a turn, watches tokens arrive as the model produces them, steers or interrupts mid-turn, and comes back later to the same conversation — branching from any earlier point rather than starting over. The conversation is a durable tree in the store the crate already keeps, so a session survives a crash the same way a run already does. `TaskContract` becomes what it always was in practice: an optional bound on a turn, or a headless one-shot for unattended work. It stops being the only way in. This is the release that makes a terminal or a desktop app possible. Until it lands, SSE is consumed internally and accumulated, events are emitted at step granularity, and there is nothing for a UI to render while the model is still typing. | outline | planned |
| 0.21.0 | The agent can plan and can ask. A todo tool lets it hold a multi-step plan the operator can watch rather than infer; a question tool lets it resolve an ambiguity about intent, which is a different thing from the approval path already in the crate — that one asks whether an action is permitted, not what the operator actually wanted. Named agent definitions give a spawned sub-agent a role, a model, and a narrowed boundary from configuration rather than from a hand-built contract, and prompt templates give an operator a repeatable way to start a turn. Repetition detection rides along: an agent that makes the same call three times in a row is not progressing, and the stall machinery added in 0.11.0 already has the signal to notice. | outline | planned |
| 0.22.0 | The agent can reach current information. Web search and fetch are declared and configured by the harness across all three providers — each of which executes them server-side — so answers arrive with the provider's own citations rather than from a scraper this crate would otherwise have had to write and maintain. The boundary is honest about what it covers. The provider dials the URL, so `Act::Net` never sees it; what the harness does is project the policy's network allow-rules onto each provider's own domain filter, so one declaration governs both and the trace records what was declared. That is a boundary enforced by the provider, and the contract says so in the same words it already uses for a stdio MCP server. Three things have to be right or the feature fails quietly rather than loudly: search results carry encrypted content that must be echoed back byte-identical, so server-tool blocks become opaque ledger entries the context assembler never compacts; a long search turn returns a paused stop reason that the run loop must resume rather than treat as an ending; and a failed search arrives as a successful HTTP response carrying an error object, which must reach the trace as a failure instead of reading as a search that found nothing. An LSP client follows in the same release if it fits: goto-definition, references, and diagnostics are what stop an agent guessing at symbol names in a large repository. | outline | planned |
