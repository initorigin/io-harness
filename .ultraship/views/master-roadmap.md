# Master roadmap

## io-harness

| Version | Outcome | Detail | Status |
| --- | --- | --- | --- |
| 0.1.0 | A developer embeds the crate, hands it one file-edit task contract, and the harness runs the loop (observe, reason, act, verify, stop) with the filesystem tool and the OpenRouter provider; the verification layer confirms the file meets the spec and the run stops on success or a step cap. | specified | released |
| 0.2.0 | A developer runs a longer, multi-step task and can trust it: step, time, and cost budgets are enforced, failed steps are retried or recovered, and a full trace plus rusqlite state make the run auditable and resumable. Verification is execution-based — the gate compiles and/or runs a test against the produced artifact, so a task cannot pass with a substring stub (0.1.0 live run showed FileContains is trivially gamed; see iterations/US-IO-HARNESS-0.2.0-I01). | specified | released |
| 0.3.0 | A developer runs a task that greps and finds across a repository and edits several files, choosing OpenRouter, Anthropic, or OpenAI as the provider. | specified | released |
| 0.4.0 | A developer runs an agent on sensitive work under an explicit permission policy: deny-by-default path rules decide which files it may read and write, and a command policy decides which binaries verification may execute. Out-of-policy actions are refused rather than performed, and actions marked sensitive stop for a human decision before they happen — either through an Approver the caller supplies in-process, or by pausing the run, persisting the pending action, and resuming once a decision arrives. Every refusal and every approve/deny is in the rusqlite trace. The policy is serde-serializable and composes in layers, so io-cli and io-studio each keep their own config over a shared base instead of each building its own permission model. | specified | released |
| 0.5.0 | A developer hands the harness one large task and a parent agent decomposes it, spawning sub-agents on demand — up to 100+ concurrently — each running its own observe/reason/act/ verify/stop loop over a shared workspace and a shared trace, with results composed back so the parent continues from what the children produced. Children can nest (spawn their own children) to a bounded depth. The 0.4.0 policy becomes a containment boundary: a child inherits its parent's policy and can only narrow it — it can never grant itself read, write, or execute the parent lacks — and the whole tree runs under one aggregate spend ceiling (agent count, tokens, cost, time) that no spawned task contract can raise. Every spawn, every parent/child edge, and every draw against the shared budget is in the rusqlite trace as one auditable graph. | specified | released |
| 0.6.0 | A developer runs a task whose generated code executes inside an ephemeral local sandbox that is created, run, captured, and destroyed per run, so execution-based verification and any agent-run command no longer compile and run model-produced code directly on the host — closing the "compiles locally, no isolation" limitation carried since 0.2.0 and made sharper by 0.5.0's many concurrent agents. The sandbox is both OS-native and OS-neutral: a single `Sandbox` trait with a real native backend per platform (macOS sandbox-exec, Linux namespaces+seccomp, Windows Job Objects) over a portable floor (ephemeral tempdir, resource caps, network denied) that compiles and runs on all three, so the same harness isolates code the same way on mac, linux, and windows. | specified | released |
| 0.7.0 | A developer starts a task and walks away: the harness runs unattended for a long horizon (24h+) with no user input, durably checkpointing after every completed step so a crash or full restart resumes the whole agent tree exactly where it stopped — completed steps are not re-run, the 0.5.0 aggregate budget is not double-charged, and an irreversible action already taken is not taken twice. A policy-required approval (0.4.0) pauses the whole tree, persists the pending action, and resumes on the human decision even across a restart in between. Ephemeral 0.6.0 sandboxes die with the process and are re-created on resume; an exec in flight at crash time is replayed idempotently. Proven by a real kill-9-then-resume-to-completion crash test plus a time-scaled long unattended run; a literal 24h wall-clock run is noted, not gated on. | specified | released |
| 0.8.0 | A developer points the harness at MCP servers and the agent uses their tools alongside the built-ins, in the same observe/reason/act/verify/stop loop — the crate becomes extensible without a fork. Because MCP servers are the first callers that can dial an arbitrary host, network egress stops being ungoverned: the 0.4.0 permission model gains a network act, so outbound calls (the provider, an HTTP MCP server, an MCP tool's own reach) are deny-by-default, layered, and either allowed, refused, or paused for a human decision by the same policy that already governs read, write, and exec. Refusals and decisions are in the rusqlite trace, a 0.5.0 child can only narrow its parent's network rules, and a network approval survives a restart under 0.7.0 durable pause. | specified | released |
| 0.9.0 | A developer extends the harness in-process without MCP: registering their own typed tools (plugins) against a public tool trait, and loading skills — instruction files that shape how an agent approaches a class of task — so io-cli and io-studio each add their own capabilities and behaviour over the shared engine. Plugin tools are governed by the same 0.4.0/0.8.0 policy and appear in the trace exactly like built-ins. | outline | planned |
| 0.10.0 | A developer runs a task over real documents: the agent creates and edits Word, Excel, PowerPoint, and PDF files, watermarks and fills PDF forms, and reads text and codes off a page through OCR and barcode/QR — with the same path policy, sandboxing, and verification that govern source edits. | outline | planned |
| 0.11.0 | A developer hands the agent an image or video alongside the task and the harness passes it through to any provider whose model accepts it, and the agent works a real git repository — reading history, staging, and committing its own work — so a run ends as reviewable version control rather than loose file edits. | hypothesis | planned |
| 1.0.0 | A developer depends on io-harness under a stable public contract: the crate API is frozen for 1.x, every public item is documented with a worked example, and the SemVer promise the product claims is one an external Rust developer can actually rely on. | hypothesis | planned |
