# Master roadmap

## io-harness

| Version | Outcome | Detail | Status |
| --- | --- | --- | --- |
| 0.1.0 | A developer embeds the crate, hands it one file-edit task contract, and the harness runs the loop (observe, reason, act, verify, stop) with the filesystem tool and the OpenRouter provider; the verification layer confirms the file meets the spec and the run stops on success or a step cap. | specified | released |
| 0.2.0 | A developer runs a longer, multi-step task and can trust it: step, time, and cost budgets are enforced, failed steps are retried or recovered, and a full trace plus rusqlite state make the run auditable and resumable. Verification is execution-based — the gate compiles and/or runs a test against the produced artifact, so a task cannot pass with a substring stub (0.1.0 live run showed FileContains is trivially gamed; see iterations/US-IO-HARNESS-0.2.0-I01). | specified | released |
| 0.3.0 | A developer runs a task that greps and finds across a repository and edits several files, choosing OpenRouter, Anthropic, or OpenAI as the provider. | specified | released |
| 0.4.0 | A developer runs an agent on sensitive work under an explicit permission policy: deny-by-default path rules decide which files it may read and write, and a command policy decides which binaries verification may execute. Out-of-policy actions are refused rather than performed, and actions marked sensitive stop for a human decision before they happen — either through an Approver the caller supplies in-process, or by pausing the run, persisting the pending action, and resuming once a decision arrives. Every refusal and every approve/deny is in the rusqlite trace. The policy is serde-serializable and composes in layers, so io-cli and io-studio each keep their own config over a shared base instead of each building its own permission model. | specified | released |
| 0.5.0 | A developer hands the harness one large task and a parent agent decomposes it, spawning sub-agents on demand — up to 100+ concurrently — each running its own observe/reason/act/ verify/stop loop over a shared workspace and a shared trace, with results composed back so the parent continues from what the children produced. Children can nest (spawn their own children) to a bounded depth. The 0.4.0 policy becomes a containment boundary: a child inherits its parent's policy and can only narrow it — it can never grant itself read, write, or execute the parent lacks — and the whole tree runs under one aggregate spend ceiling (agent count, tokens, cost, time) that no spawned task contract can raise. Every spawn, every parent/child edge, and every draw against the shared budget is in the rusqlite trace as one auditable graph. | specified | released |
| 0.6.0 | A developer runs a task whose generated code executes inside an ephemeral local sandbox that is created, run, captured, and destroyed per run, so execution-based verification and any agent-run command no longer compile and run model-produced code directly on the host — closing the "compiles locally, no isolation" limitation carried since 0.2.0 and made sharper by 0.5.0's many concurrent agents. The sandbox is both OS-native and OS-neutral: a single `Sandbox` trait with a real native backend per platform (macOS sandbox-exec, Linux namespaces+seccomp, Windows Job Objects) over a portable floor (ephemeral tempdir, resource caps, network denied) that compiles and runs on all three, so the same harness isolates code the same way on mac, linux, and windows. | specified | released |
| 0.7.0 | A developer starts a task and walks away: the harness runs unattended for a long horizon (24h+) with no user input, durably checkpointing after every completed step so a crash or full restart resumes the whole agent tree exactly where it stopped — completed steps are not re-run, the 0.5.0 aggregate budget is not double-charged, and an irreversible action already taken is not taken twice. A policy-required approval (0.4.0) pauses the whole tree, persists the pending action, and resumes on the human decision even across a restart in between. Ephemeral 0.6.0 sandboxes die with the process and are re-created on resume; an exec in flight at crash time is replayed idempotently. Proven by a real kill-9-then-resume-to-completion crash test plus a time-scaled long unattended run; a literal 24h wall-clock run is noted, not gated on. | specified | released |
| 0.8.0 | A developer points the harness at MCP servers and the agent uses their tools alongside the built-ins, in the same observe/reason/act/verify/stop loop — the crate becomes extensible without a fork. Because MCP servers are the first callers that can dial an arbitrary host, network egress stops being ungoverned: the 0.4.0 permission model gains a network act, so outbound calls (the provider, an HTTP MCP server, an MCP tool's own reach) are deny-by-default, layered, and either allowed, refused, or paused for a human decision by the same policy that already governs read, write, and exec. Refusals and decisions are in the rusqlite trace, a 0.5.0 child can only narrow its parent's network rules, and a network approval survives a restart under 0.7.0 durable pause. | specified | released |
| 0.8.1 | An operator can trust that a passing execution gate was not defeated by the file it verified. The subject file can no longer shadow what the criterion names, so the recorded bypass — a `#[macro_export] macro_rules! assert` making `assert!(false, "this gate can never pass")` report ok — fails, and so does the same attack through `WorkspaceTestPasses`. See iterations/US-IO-HARNESS-0.8.0-I01. | specified | released |
| 0.9.0 | A developer extends the harness in-process without MCP: their own typed tools registered against a public tool trait, compiled into their binary, offered to the model beside the built-ins and governed by the same 0.4.0/0.8.0 policy and trace; and skills — instruction files discovered from a directory, whose body shapes how the agent approaches a class of task. io-cli and io-studio each add their own capabilities and behaviour over the shared engine. No dynamic loading and no plugin ABI — out-of-process extension is what 0.8.0's MCP client is for. Skills carry instructions, not code. | specified | released |
| 0.9.1 | A developer on Linux or Windows gets the isolation and verification the crate has claimed since 0.3.0 and 0.6.0, or is told plainly that they do not. 0.9.0 added the repository's first CI matrix and it immediately disproved three standing claims: on Linux the execution-based verification gate does not work at all (7 `verify::tests` failures, `passes_guarded` returning false) and the sandbox CPU and memory caps never fire (`cap_hit: None` where `Some(Cpu)` is expected); on Windows no Job Object is ever created, so containment is the portable floor and the suite hangs rather than being killed by a cap. 0.9.0 corrected the false `Backend::WindowsJobObject` label and documented the gap; this release closes it — the Linux verify and cap failures are root-caused and fixed, the Windows suite terminates, and the Windows native backend is either implemented against the Win32 job-object API or formally declared unsupported-for-containment in the roadmap rather than left as an unfulfilled promise. | 0.10.0 | A developer runs a long task and the agent's context stays relevant instead of merely growing. What the model sees each turn is assembled to fit a stated share of the token budget: superseded observations are compacted, an observation invalidated by a later write is re-read rather than trusted, and each tool result is bounded where it enters the context rather than where it enters the trace. The agent also keeps durable memory — facts and decisions it writes deliberately and recalls on a later run over the same workspace — so a second run does not rediscover what the first established. Closes the context-construction and state-and-memory gaps; see iterations/US-IO-HARNESS-0.9.0-I01. | specified | released |
| 0.11.0 | A developer's long unattended run survives the failures that end runs today, not just the crashes 0.7.0 covers. | 0.12.0 | A developer watching a run sees it as it happens, and a developer measuring the harness can. | 0.13.0 | A developer who resumes an interrupted run gets the run they had, not a similar one. Resume today restores only the durable half — the step it reached, what it spent, how long it has been alive — and silently substitutes the rest. Two things go missing, and both are the same defect. The permission boundary: `resume` and `resume_observed` hardcode `Policy::permissive()` and `ApproveAll` for every workspace run (src/run.rs:334-356), so a caller who started under a restrictive policy through `run_with` and resumes after a crash gets an agent with no boundary, and no policy-preserving general resume exists to reach for — `resume_with_decision` takes a policy but demands a `request_id` and a pending `Decision`, so it only serves a run that paused for approval. The crate states the opposite principle 60 lines earlier at src/run.rs:270-279, where single-file mode refuses a policy loudly precisely so a caller never believes a boundary is enforced when nothing is checking. And the assembled half: the observation ledger the 0.10.0 context assembler builds is in memory only, built fresh at src/run.rs:1242 and :1821 after the resume step is already known, so a resumed workspace or sub-agent run re-derives its context from the workspace and asks the model a different question than the process before it would have. After this release a resumed run carries the policy it was started under and the context it had: `resume` gains a policy-bearing form, a run that was started under a policy cannot be silently resumed without one, the ledger is durable and restored, and a recorded case replays identically across an interruption in every loop rather than only the single-file one. Pulled ahead of documents because a boundary a caller believes is enforced and is not is worth more than breadth, and because both halves live in the same functions — worth touching resume once, not twice. The ledger half was found by 0.12.0's replay work and recorded in iterations/US-IO-HARNESS-0.12.0-I01, where 0.12.0 shipped the honest boundary instead: a replay that cannot reproduce a request refuses loudly rather than answering from the wrong recording. | specified | released |
